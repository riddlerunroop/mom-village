## Native app — Phase 6 (Vaccinations + Memories) built and synced, 2026-07-31

Sixth phase off the agreed 8-phase plan. Built the two bounded 0-3 additions — vaccination tracking and voice/photo memories + recall — replacing the two placeholder-free gaps left after Phase 1 (these were never given their own tab, same as web, since they're deliberately bounded additions, not a 6th pillar). Reuses `user_vaccination_records`, `user_voice_logs`, `user_photo_logs`, plus the `vaccination-cards`/`voice-logs`/`memory-photos` private Storage buckets exactly as they exist for web (migrations 12/18). No new tables needed.

**Real architectural first for this project: a web-side code change was required to support the native app.** Every phase before this one was purely additive on the native side — direct Supabase table queries, zero web changes. This phase's two AI-backed features (Claude Vision reading a vaccination card, Whisper transcribing a voice note, Claude answering a recall question) all run through the *website's existing Next.js API routes* (`/api/vaccination/extract`, `/api/memories/transcribe`, `/api/memories/recall`) rather than duplicating server-side secrets into the mobile app — but those routes were cookie-auth-only (`@supabase/ssr`), which doesn't exist for a native app with no browser cookies. Fixed with a new shared helper, **`src/lib/supabase/apiAuth.ts`** (`getAuthedSupabase(req)`): if the request carries an `Authorization: Bearer <token>` header, it validates that token directly against Supabase; otherwise it falls through to the exact original cookie-based path, completely unchanged for every existing web request. All three routes were updated to use this helper in place of the old cookie-only client. Verified via `npx tsc --noEmit` and `npx eslint` on the whole repo (zero new errors) plus a `git stash` check confirming one pre-existing, unrelated FormData type error in `transcribe/route.ts` predates this change and isn't a regression.

**Built:**
- `mobile/lib/api.ts` — `authedFetch(path, init)`, a thin wrapper that reads the native Supabase session's access token and attaches it as a Bearer header before calling `https://www.momvillage.in<path>` — the one place the native app calls back into the website's own server instead of Supabase directly.
- `mobile/lib/vaccinationSchedule.ts` — verbatim port of the web UIP schedule/logic (`expandScheduleOccurrences`, `getOccurrenceStatus`, `ageInDays`, `doseLabel`, `occurrenceOptions`), pure TS, no browser dependency either side.
- `mobile/app/vaccinations.tsx` — schedule list with the same overdue/due-soon/upcoming/given status logic and banner as web's `dashboard/vaccinations/page.tsx`, gated on subscription + baby already born.
- `mobile/app/vaccinations-log.tsx` — photo (camera or library, via `expo-image-picker`) → sent to `/api/vaccination/extract` via `authedFetch` → AI vaccine/date suggestion shown for her review (never auto-saved) → she picks the actual dose from a dropdown and confirms/edits the date → card photo uploaded to the `vaccination-cards` bucket → upserted into `user_vaccination_records`, same shape as web.
- `mobile/app/memories.tsx` — three pieces in one screen, same as web's `MemoriesClient.tsx`: a recall question box (`authedFetch` to `/api/memories/recall`); voice recording via `expo-av`'s `Audio.Recording` API → `authedFetch` multipart POST to `/api/memories/transcribe` → review/edit transcript before saving to `user_voice_logs`; photo logging via `expo-image-picker` → uploaded to the `memory-photos` bucket → saved to `user_photo_logs` with an optional caption; a merged, reverse-chronological timeline of both log types with signed photo URLs (`createSignedUrls`, 1hr).
- `mobile/app.json` — added `expo-image-picker` (camera + photo-library permission strings) and `expo-av` (microphone permission string) as config plugins.
- `mobile/package.json` — added `expo-image-picker@~17.0.11`, `expo-av@~16.0.8`, `expo-file-system@~19.0.23` (exact SDK-54-compatible versions, read directly from `node_modules/expo/bundledNativeModules.json` since this sandbox's network proxy blocks the `npx expo install` compatibility check — same recurring workaround as every prior phase's dependency installs).
- `mobile/app/(tabs)/index.tsx` — Today tab's "Track vaccinations" and "Log a memory" quick actions now route to the new native screens (`router.push("/vaccinations")` / `"/memories"`) instead of opening the website in the phone's browser. "Past months" still opens the website — the native archive view isn't built (out of this phase's scope; nothing currently plans to build it, since Today already shows the current month and past months are a lower-value native target).

**One real SDK-54 API gotcha caught by `tsc`, not silently shipped:** `expo-file-system` 19.x (this SDK's version) replaced the old `readAsStringAsync`/`EncodingType` API with a new File/Directory-class API by default — the old API still exists, but only under an `expo-file-system/legacy` subpath import. `memories.tsx`'s photo-upload base64 read uses this legacy subpath explicitly, with a comment explaining why, rather than fighting the new API for a one-off base64 read.

Verified clean on `npx tsc --noEmit`. Built and checked in the sandbox's native filesystem, then synced into the mounted `mobile/` folder — `diff -rq` confirmed byte-identical across `app/`, `lib/`, `package.json`, and `app.json` after the sync. Not yet pushed via GitHub Desktop (native side) or via GitHub Desktop (the three web route files + new `apiAuth.ts` helper) — same "she pushes when ready" pattern as every other change in this project. **Both the mobile and web changes need to go out together** — the native screens won't work until the website's updated API routes are actually deployed.

**Known gaps, flagged rather than silently skipped:** no native due-date push reminder for vaccinations yet (native push is Phase 8). No native "past months" vaccination history view — only the current schedule. Voice recording uses `expo-av`, which Expo has begun deprecating in favor of `expo-audio`/`expo-video` in newer SDKs — fine on SDK 54 (still the actively-supported store-installable version per the SDK-mismatch note above), worth revisiting on a future SDK bump.

## Library pillar — build started 2026-07-24, all six books now readable in-app (subscriber reading experience only)

All six Library books (three Wealth/finance, three Parenting) are now content-locked (see above). Roop's own framing for the next step: "one more left on parenting and then we can build the library" — build started right after parenting book 3 locked.

**Scope decision, confirmed 2026-07-24.** The full Library access model (non-subscribers buy individually/bundled, subscribers get everything included but in-app-only, downloads are always a separate paid action even for subscribers — see the access-model decision logged under Wealth above) needs Razorpay, which is deliberately being built last. Rather than pull Razorpay forward, Roop chose to scope this round to **the subscriber in-app reading experience only** — a book catalog page plus an in-app reader for subscribers, no purchase/bundle/download flow yet. That piece waits for Razorpay as originally sequenced.

**A real page-flip book reader, not a plain scroller.** Roop asked for something closer to a real book — pages that visually turn/fold like an actual page, with a page-turn sound, rather than a simple scrolling chapter view (she'd seen this in another app). Confirmed feasible and built using `react-pageflip` (the `page-flip` engine under the hood), which gives realistic drag-to-turn animation with a curl/shadow effect. Important technical note for future sessions: making pages "flip" requires the book to use **fixed-size virtual pages** (content is pre-paginated into fixed chunks, not a responsive scroll) — the whole book then scales as a unit to fit the screen via `size="stretch"` with min/max bounds, so page breaks stay consistent across devices even though the physical page looks bigger on desktop than on a phone.

**Prototype built with one book first, as agreed — "Money, Understood" (the shortest of the six, ~17,000 words).** Roop explicitly asked to see/approve this before the other five get converted the same way, given it's a real format decision. Pipeline built:

- `docx → HTML (pandoc) → parsed content blocks → paginated JSON`, done as an offline conversion (not at runtime). The HTML parse (via BeautifulSoup) walks the manuscript and classifies each element into one of five block types: paragraph, heading, list, "box" (the manuscript's single-cell callout tables like REMEMBER THIS / TRY THIS TODAY — rendered as styled callout cards), or "table" (real multi-column data tables, e.g. the product-comparison and resource-directory tables — large tables are automatically split into smaller chunks of ~3 data rows each so they never overflow a single page).
- A greedy pagination pass packs these blocks onto virtual pages using a weighted character budget (~620 weighted characters/page, with headings/boxes/tables weighted heavier than their raw character count to account for the extra visual space they take). Money, Understood paginated to **306 pages** at this budget — every chapter always starts a fresh page.
- Output stored as static JSON at `src/content/library/money-understood.json` (not a database table — book content is fixed editorial content, not user data, so no migration was needed for this).
- Each book's actual cover image (already embedded in its locked manuscript docx) was extracted directly from the docx's `word/media/` folder for reuse — all six cover PNGs now live in `public/library-covers/`, used both on the reader's front cover page and the catalog thumbnails.

**Page-turn sound effect — synthesized, not sourced.** Rather than risk a copyrighted/licensed sound clip, a short (~0.3s) "swish" sound was synthesized programmatically in Python (filtered white noise with a fast-attack/quick-decay envelope, plus a very brief low thump at the very start to suggest the page corner catching) and encoded to `public/sounds/page-turn.mp3` (~2.5KB). Royalty-free by construction since nothing was sourced externally.

**Build:**

- `react-pageflip` added to `package.json` dependencies (no peer-dependency conflicts with React 19; Vercel will install it automatically on next deploy, same pattern as `@anthropic-ai/sdk` earlier). No official TypeScript types exist for this package, so a hand-written ambient declaration was added at `src/types/react-pageflip.d.ts` covering the props actually used.
- `src/lib/library.ts` — static metadata for all six books (title, tagline, series, cover path, and a `hasReader` flag).
- `src/types/library-content.ts` — shared types for the paginated page/block JSON shape.
- `src/components/BookReader.tsx` — the actual flip-book reader (client component): renders a cover page (the real cover image), one rendered page per JSON page entry (chapter-start pages get a kicker/title/epigraph header), and a simple "end of book" closing page. Plays the page-turn sound on every flip via a hidden `<audio>` element. Desktop gets hover arrow buttons beside the book; mobile gets Prev/Next buttons below it; both plus native swipe/drag (built into the library) all work.
- `src/app/dashboard/library/page.tsx` — rewritten from the placeholder into a real catalog: both series shown with real cover art in a grid, subscription-gated the same way as every other pillar (`LockedPreview` for non-subscribers).

Could not run a full `next build` inside this sandbox because Google Fonts (Fraunces/Karla, fetched at build time by `next/font/google`) aren't reachable from this environment's network allowlist — this is a sandbox limitation unrelated to the change and will not occur on Vercel's build, which has normal internet access.
